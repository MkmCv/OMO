# 第二章：骨架 — 插件入口与初始化

## 概述

本章逐行解读 OmO 的 6 个核心文件，理解插件从加载到就绪的完整过程。

## 2.1 入口 — src/index.ts

整个项目只有一个导出，90 行代码：

```typescript
const OhMyOpenCodePlugin: Plugin = async (ctx) => {
  // ctx.client  — OpenCode SDK 客户端（创建会话、发消息、管理代理）
  // ctx.directory — 当前工作目录
}
export default OhMyOpenCodePlugin
```

### 热重载支持

```typescript
// 第 18 行：全局保存当前插件的销毁函数
let activePluginDispose: PluginDispose | null = null

// 第 29 行：每次加载先销毁上一次的实例
await activePluginDispose?.()
```

配置改了不用重启 OpenCode，OmO 会自动销毁旧实例、创建新实例。

### Hook 开关机制

```typescript
const disabledHooks = new Set(pluginConfig.disabled_hooks ?? [])
const isHookEnabled = (hookName: HookName): boolean => !disabledHooks.has(hookName)
```

闭包模式。后续创建每个 Hook 前都会检查 `isHookEnabled`。用户可在配置里关闭任意 Hook：
```jsonc
{ "disabled_hooks": ["model-fallback", "auto-update-checker"] }
```

### 5 步初始化顺序

```
loadPluginConfig()      ← 第 1 步：配置
      ↓
createManagers()        ← 第 2 步：管理器（依赖配置）
      ↓
createTools()           ← 第 3 步：工具（依赖管理器）
      ↓
createHooks()           ← 第 4 步：Hook（依赖管理器 + 工具的 Skill 输出）
      ↓
createPluginInterface() ← 第 5 步：接口（依赖所有上述产出）
```

每一步都依赖上一步的输出，不能并行，必须串行。

## 2.2 配置加载 — src/plugin-config.ts

### 配置来源与优先级

```
用户级：~/.config/opencode/oh-my-opencode.jsonc
项目级：<项目目录>/.opencode/oh-my-opencode.jsonc
```

- .jsonc 优先于 .json（detectConfigFile 自动探测）
- 用户级 = 全局默认值
- 项目级 = 覆盖用户级

### 合并规则（mergeConfigs）

```typescript
return {
  ...base,
  ...override,                                  // 浅层覆盖
  agents: deepMerge(base.agents, override.agents),       // 深度合并
  categories: deepMerge(base.categories, override.categories), // 深度合并
  disabled_agents: [...new Set([...base, ...override])],  // Set 并集
  disabled_hooks: [...new Set([...base, ...override])],   // Set 并集
  // ...其他 disabled_* 同理
}
```

- agents/categories 用深度合并（项目级可以只覆盖某个代理的某个字段）
- disabled_* 用 Set 并集（两边的禁用项都保留，不会互相覆盖）

### 容错设计（parseConfigPartially）

如果整体校验失败，不崩溃，而是逐段校验：

```typescript
for (const key of Object.keys(rawConfig)) {
  const sectionResult = OhMyOpenCodeConfigSchema.safeParse({ [key]: rawConfig[key] })
  if (sectionResult.success) {
    partialConfig[key] = parsed[key]  // 有效段保留
  } else {
    invalidSections.push(...)          // 无效段跳过并记录
  }
}
```

这意味着用户写错了 `categories` 配置，不会影响 `agents` 的正常加载。

## 2.3 管理器创建 — src/create-managers.ts

81 行代码，创建 4 个管理器：

| 管理器 | 类 | 职责 |
|--------|---|------|
| tmuxSessionManager | TmuxSessionManager | 管理 tmux 窗格的创建、布局、清理 |
| backgroundManager | BackgroundManager | 管理后台代理任务的生命周期 |
| skillMcpManager | SkillMcpManager | 管理 Skill 对应的 MCP 服务器 |
| configHandler | createConfigHandler() | 向 OpenCode 注册代理配置 |

### 管理器之间的协作（回调解耦）

```typescript
const backgroundManager = new BackgroundManager(ctx, pluginConfig.background_task, {
  onSubagentSessionCreated: async (event) => {
    // BM 不直接操作 tmux
    // 而是通知 tmux 管理器"有新子代理会话了"
    await tmuxSessionManager.onSessionCreated({
      type: "session.created",
      properties: { info: { id: event.sessionID, parentID: event.parentID, title: event.title } },
    })
  },
  onShutdown: async () => {
    await tmuxSessionManager.cleanup()
  },
})
```

**设计原则**：管理器之间不互相引用，通过回调解耦。BM 不知道 tmux 的存在，只知道"创建会话后要调一个回调"。

## 2.4 工具注册 — src/create-tools.ts

```typescript
export async function createTools(args): Promise<CreateToolsResult> {
  // 1. 创建 Skill 上下文（唯一的 async 步骤）
  const skillContext = await createSkillContext({ directory, pluginConfig })
  // → 从 6 个来源发现所有 Skill
  // → 合并、去重、解析元数据
  // → 产出：mergedSkills, availableSkills, browserProvider, disabledSkills

  // 2. 解析 Category 配置
  const availableCategories = createAvailableCategories(pluginConfig)
  // → 8 个默认类别 + 用户自定义类别
  // → 每个类别有 name, description, model

  // 3. 注册工具
  const { filteredTools, taskSystemEnabled } = createToolRegistry({
    ctx, pluginConfig, managers, skillContext, availableCategories,
  })
  // → 26 个工具注册到 OpenCode
  // → 被 disabled_tools 过滤的工具不注册

  return { filteredTools, mergedSkills, availableSkills, availableCategories, ... }
}
```

返回值不仅有工具，还有 Skill 和 Category 信息 — 这些会传给 createHooks()，用于 Skill 提醒等 Hook。

## 2.5 Hook 组装 — src/create-hooks.ts

3 层 Hook，有依赖关系：

```typescript
export function createHooks(args) {
  // 第 1 层：Core（39 个）— 基础功能
  const core = createCoreHooks({ ctx, pluginConfig, modelCacheState, isHookEnabled })
  //  ├── createSessionHooks()     23 个（模型切换、think mode、ralph loop...）
  //  ├── createToolGuardHooks()   12 个（写保护、注释检查、编辑恢复...）
  //  └── createTransformHooks()    4 个（消息变换、关键词检测...）

  // 第 2 层：Continuation（7 个）— 依赖 Core 的 sessionRecovery
  const continuation = createContinuationHooks({
    ..., sessionRecovery: core.sessionRecovery,  // ← 依赖上一层
  })

  // 第 3 层：Skill（2 个）— 需要 Skill 列表
  const skill = createSkillHooks({ ..., mergedSkills, availableSkills })

  // 合并所有 Hook + 销毁函数
  return {
    ...core,
    ...continuation,
    ...skill,
    disposeHooks: () => { disposeCreatedHooks(hooks) },
  }
}
```

**关键约束**：3 层必须串行创建，因为 Continuation 依赖 Core 的 `sessionRecovery`。

### dispose 机制

有些 Hook 有内部状态（定时器、事件监听器），需要在插件卸载时清理：

```typescript
export function disposeCreatedHooks(hooks) {
  hooks.runtimeFallback?.dispose?.()
  hooks.todoContinuationEnforcer?.dispose?.()
  hooks.autoSlashCommand?.dispose?.()
}
```

## 2.6 插件接口 — src/plugin-interface.ts

最终产出 — 暴露给 OpenCode 的拦截点：

```typescript
return {
  tool: tools,                    // 26 个自定义工具

  config: managers.configHandler,  // 代理注册（告诉 OpenCode 有哪些代理可用）

  "chat.message": createChatMessageHandler({ ctx, pluginConfig, hooks }),
  // ↑ 最核心的拦截点，每条消息发送前都经过它

  "chat.params": createChatParamsHandler({ anthropicEffort }),
  // ↑ 修改 API 请求参数（如 thinking effort）

  "chat.headers": createChatHeadersHandler({ ctx }),
  // ↑ 注入认证头

  "experimental.chat.messages.transform": createMessagesTransformHandler({ hooks }),
  // ↑ 变换消息列表（压缩旧消息）

  "experimental.chat.system.transform": createSystemTransformHandler(),
  // ↑ 变换系统提示

  event: createEventHandler({ ctx, pluginConfig, managers, hooks }),
  // ↑ 第二核心拦截点，响应所有事件（模型出错、会话空闲、后台完成...）

  "tool.execute.before": createToolExecuteBeforeHandler({ ctx, hooks }),
  // ↑ 工具执行前（权限检查、上下文注入）

  "tool.execute.after": createToolExecuteAfterHandler({ ctx, hooks }),
  // ↑ 工具执行后（输出截断、错误恢复、Skill 提醒）

  "tool.definition": async (input, output) => {
    await hooks.todoDescriptionOverride?.["tool.definition"]?.(input, output)
  },
  // ↑ 修改工具定义（如 TODO 工具的描述）
}
```

### 设计模式：工厂函数 + 依赖注入

每个 Handler 都是工厂函数：

```typescript
// 不是直接导出处理函数
export function createChatMessageHandler(deps) {
  return async (input, output) => {
    // 使用 deps.hooks.modelFallback 等
  }
}
```

好处：
- 依赖明确（函数签名说明需要什么）
- 方便测试（可以注入 mock）
- 解耦（Handler 不知道其他 Handler 的存在）

## 总结：初始化数据流

```
                     pluginConfig
                    ╱     │      ╲
                   ╱      │       ╲
            managers    tools     hooks
                 ╲       │       ╱
                  ╲      │      ╱
                 pluginInterface
                       │
                       ▼
                   OpenCode
```

- pluginConfig 是所有步骤的共同输入
- managers 被 tools 和 hooks 使用
- tools 的 Skill 输出被 hooks 使用
- 最终 pluginInterface 把所有产出组装成 OpenCode 能理解的格式
