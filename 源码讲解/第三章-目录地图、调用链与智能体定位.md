# 第三章：目录地图、调用链与智能体定位

## 本章目标

这一章不是逐行讲代码，而是给后来接手的 AI 一个足够稳定的“仓库脑图”：

1. 先知道每个目录是干什么的。
2. 再知道插件从启动到运行的主调用链。
3. 最后知道每个内置 AI 的定位、触发入口和上下游关系。

如果你是新的 AI，读完本章后，应该能回答这 4 个问题：

- 这个仓库真正的运行入口在哪里。
- `agent / tool / hook / feature` 四层分别负责什么。
- `task(category=...)` 和 `task(subagent_type=...)` 到底走哪条链。
- Sisyphus、Hephaestus、Prometheus、Atlas、Sisyphus-Junior 这些 AI 各自扮演什么角色。

## 一个重要原则：哪里是真正的“源码真相”

这个仓库里有大量自动生成的 `AGENTS.md`，它们很适合快速导航，但不是绝对真相。

优先级建议：

```text
真实运行代码（*.ts）
  > 目录级 AGENTS.md（生成的导航快照）
  > README / 中文讲解 / 其他说明文档
```

原因很简单：说明文档可能滞后，运行代码不会撒谎。

### 1. `src/`

这就是插件本体。

### 2. `docs/`

面向使用者的文档。它告诉你产品想做什么，但不告诉你运行时到底怎么串。

### 3. `packages/`

发布平台二进制用的子包目录，比如 Linux/macOS/Windows 各架构包。对理解插件逻辑帮助不大。

### 4. `bin/`

CLI 实际可执行入口在这里，主要是把 `oh-my-opencode` 命令引导到编译后的实现。

### 5. `script/`

构建和发布脚本目录，目前能看到：

```text
build-binaries.ts
build-schema.ts
build-schema-document.ts
generate-changelog.ts
publish.ts
```

所以它是“构建/发版链”而不是“运行链”。

### 6. `tests/`

补充测试资源，尤其像 `tests/hashline/` 这种更偏专项/夹具。

### 7. `.opencode/`

这是项目级 OpenCode 配置内容。

当前仓库里能看到：

```text
.opencode/command/*.md
.opencode/skills/*/SKILL.md
.opencode/background-tasks.json
```

它的意义是：这个仓库本身就在演示和消费自己的 command / skill 体系。

### 8. `.sisyphus/`

这是 Sisyphus/Prometheus/Atlas 工作流目录。

当前仓库提交里能看到：

```text
.sisyphus/rules/modular-code-enforcement.md
```

但运行时更重要的是这些约定路径：

```text
.sisyphus/plans/*.md
.sisyphus/boulder.json
.sisyphus/ralph-loop.local.md
```

也就是说，Prometheus 写计划，Atlas 读计划继续执行，很多状态都围绕 `.sisyphus/` 运转。

### 9. `源码讲解/`

这是当前最适合“让其他 AI 快速上手”的中文阅读入口，因为它直接围绕仓库本身组织。

## 二、`src/` 目录，一个一个看

这里才是核心。

| 目录/文件 | 定位 | 上游是谁 | 下游是谁 |
|---|---|---|---|
| `index.ts` | 插件总入口 | OpenCode 宿主 | managers/tools/hooks/plugin-interface |
| `plugin-config.ts` | 配置加载与合并 | `index.ts` | 全局 `pluginConfig` |
| `create-managers.ts` | 长生命周期管理器工厂 | `index.ts` | tools / event / hooks |
| `create-tools.ts` | skill/category/tool 组装层 | `index.ts` | plugin tool registry |
| `create-hooks.ts` | hook 分层组装层 | `index.ts` | plugin handlers |
| `plugin-interface.ts` | 向 OpenCode 暴露 8 个 hook handler | `index.ts` | OpenCode 宿主 |
| `agents/` | agent 定义、prompt、模型选择入口 | config handler | OpenCode agent config / delegation |
| `plugin-handlers/` | `config` 钩子专用 6 阶段注册流水线 | `createManagers()` | OpenCode config |
| `plugin/` | 运行时 glue 层，接 8 个 OpenCode hook | `plugin-interface.ts` | hooks/tools/managers |
| `hooks/` | 48 个生命周期 hook 的真正实现 | `createHooks()` | chat/event/tool 生命周期 |
| `tools/` | 26 个工具的真正实现 | `createTools()` | agent runtime |
| `features/` | 可复用子系统，给 tools/hooks/plugin 用 | managers/tools/hooks/plugin | 各业务层 |
| `config/` | Zod schema 和类型系统 | `plugin-config.ts` | 全局配置读取 |
| `shared/` | 通用能力：日志、模型解析、路径、tmux 等 | 几乎所有层 | 几乎所有层 |
| `mcp/` | 内置 MCP 定义 | config handler | OpenCode MCP 注册 |
| `cli/` | install/run/doctor/mcp-oauth 命令 | 人类/CI | 插件安装和诊断链 |
| `openclaw/` | 外部唤醒/网关桥接能力 | 可选集成 | tmux / 外部 reply 通道 |

下面分目录说。

### 1. `src/index.ts`

这是宿主唯一调用入口。

它做 5 件事：

```text
loadPluginConfig
  -> createManagers
  -> createTools
  -> createHooks
  -> createPluginInterface
```

理解这个文件，就理解了整个插件“怎么装起来”。

### 2. `src/plugin-config.ts`

它只管一件事：把“用户级配置 + 项目级配置”合成最终配置。

关键点：

- `agents` / `categories` / `claude_code` 是深合并
- `disabled_*` 是集合并集
- 支持 JSONC
- 整体校验失败时会做 partial parse，尽量不让插件直接崩

所以它是“配置入口”，不是“运行时决策入口”。

### 3. `src/create-managers.ts`

这里创建 4 个长生命周期对象：

- `TmuxSessionManager`
- `BackgroundManager`
- `SkillMcpManager`
- `configHandler`

你可以把它理解成“插件底盘层”。

### 4. `src/create-tools.ts`

这里不是工具实现，而是工具装配：

1. 建 `SkillContext`
2. 算 `AvailableCategories`
3. 用 `createToolRegistry()` 把工具注册出来

所以这是“工具装配层”，不是“工具业务层”。

### 5. `src/create-hooks.ts`

这里不是 hook 逻辑本体，而是分层装配器：

```text
Core Hooks
  = Session Hooks
  + Tool Guard Hooks
  + Transform Hooks

Continuation Hooks
Skill Hooks
```

它决定“哪些 hook 一起工作”，不是“hook 做什么”。

### 6. `src/plugin-interface.ts`

把前面所有产物挂到 OpenCode 的 hook 名字上：

```text
config
tool
chat.message
chat.params
chat.headers
event
tool.execute.before
tool.execute.after
experimental.chat.messages.transform
experimental.chat.system.transform
tool.definition
```

这就是插件真正对宿主暴露的边界。

### 7. `src/agents/`

这是“人格层 + prompt 层 + agent 注册层”。

不要把它理解成“调度层”。调度不在这里，调度在：

- `plugin-handlers/agent-config-handler.ts`
- `plugin/chat-message.ts`
- `plugin/event.ts`
- `tools/delegate-task/*`

`agents/` 只定义：

- 这个 agent 是谁
- 用什么模型
- 有什么 prompt
- 有哪些权限/限制
- 在 Sisyphus/Atlas 的可选 agent 列表里怎么展示

### 8. `src/plugin-handlers/`

这是 `config` 钩子的专属流水线。

它的职责不是运行时处理消息，而是“向 OpenCode 注册能力”。

关键顺序：

```text
applyProviderConfig
-> loadPluginComponents
-> applyAgentConfig
-> applyToolConfig
-> applyMcpConfig
-> applyCommandConfig
```

这条链决定 OpenCode 最终看到哪些 agent、tools、mcps、commands。

### 9. `src/plugin/`

这是运行时 glue 层。

如果说：

- `hooks/` 是功能零件
- `tools/` 是执行能力
- `features/` 是底层子系统

那么 `plugin/` 就是把这些能力接到 OpenCode 生命周期上的转接板。

这里最关键的文件是：

```text
chat-message.ts
event.ts
tool-execute-before.ts
tool-execute-after.ts
tool-registry.ts
skill-context.ts
```

### 10. `src/hooks/`

这是生命周期治理层。

它不提供业务功能，而是约束、修正、增强运行过程。

可以粗分成 5 类：

- Session 类：错误恢复、fallback、think mode、ralph loop、start-work
- Tool Guard 类：写保护、规则注入、注释检查、hashline、json 恢复
- Transform 类：context 注入、keyword detector、thinking 校验
- Continuation 类：todo continuation、atlas、background notification
- Skill 类：category skill reminder、auto slash command

### 11. `src/tools/`

这是 agent 真正能调用的执行面。

不要把所有工具一视同仁。这里有两条最重要的工具链：

1. `task`
2. `call_omo_agent`

前者是新主线，后者更像直接点名调用。

### 12. `src/features/`

这是“复用型子系统层”，不是直接暴露给宿主的层。

几个最关键的 feature：

- `background-agent/`：后台任务生命周期
- `tmux-subagent/`：tmux pane/session 管理
- `opencode-skill-loader/`：skill 发现与合并
- `skill-mcp-manager/`：skill 绑定的 MCP 生命周期
- `boulder-state/`：Prometheus/Atlas 工作状态
- `context-injector/`：AGENTS/README 注入

### 13. `src/config/`

这个目录就是 schema 层。

它不做业务，只定义：

- 什么配置是合法的
- 默认值怎么落
- agent/category/hook 名字有哪些

### 14. `src/shared/`

横切能力层。

最重要的不是“多”，而是“到处都用”。

尤其关注：

- `logger.ts`
- 模型解析相关
- provider / fallback chain
- 路径和配置目录解析
- OpenCode 兼容工具

### 15. `src/mcp/`

定义内置 MCP：

- `websearch`
- `context7`
- `grep_app`

它们不在运行时主动发力，而是在 config 阶段被注册进 OpenCode。

### 16. `src/cli/`

这条线主要服务安装、运行、诊断：

- `install`
- `run`
- `doctor`
- `mcp-oauth`

它和插件本体共享一些 schema / model resolution 逻辑，但不是同一条运行路径。

### 17. `src/openclaw/`

这是一个外围桥接能力，负责外部 wake gateway、reply listener、tmux tail 捕获之类。

对理解 OmO 的主插件链不是第一优先级，但如果看到外部通知/网关/回传，就要来这里。

## 三、先记住两条大链：启动链和运行链

## 3.1 启动链

```text
OpenCode 宿主
  -> 加载插件默认导出
  -> src/index.ts
      -> loadPluginConfig()
      -> createManagers()
      -> createTools()
      -> createHooks()
      -> createPluginInterface()
  -> OpenCode 获得一组 hook handlers
```

启动链的重点不是 agent，而是把能力装起来。

## 3.2 配置注册链

这是 `config` 钩子做的事：

```text
OpenCode 触发 config hook
  -> plugin-handlers/config-handler.ts
      -> applyProviderConfig()
      -> loadPluginComponents()
      -> applyAgentConfig()
      -> applyToolConfig()
      -> applyMcpConfig()
      -> applyCommandConfig()
  -> OpenCode 拿到最终 agent/tool/mcp/command 配置
```

这条链的意义是：OmO 不是只“自己有工具”，而是会改写 OpenCode 眼里的全局能力空间。

## 四、运行时最重要的 3 条链

## 4.1 消息链：用户一句话怎么进入系统

```text
用户消息
  -> chat.message
      -> plugin/chat-message.ts
          -> 设置 session agent / model
          -> stopContinuationGuard
          -> backgroundNotificationHook
          -> runtimeFallback
          -> keywordDetector
          -> thinkMode
          -> claudeCodeHooks
          -> autoSlashCommand
          -> noSisyphusGpt / noHephaestusNonGpt
          -> startWork
          -> ultrawork model override
```

这意味着：

- `chat.message` 是入口治理点
- 关键词模式、模型限制、slash command 自动识别都在这里发生
- `/start-work` 也是从这里把 session agent 改成 `atlas`

## 4.2 工具链：agent 调工具时发生什么

```text
agent 发出 tool call
  -> tool.execute.before
      -> 写保护 / 规则注入 / README 注入 / AGENTS 注入
      -> comment checker / non-interactive env / atlas policy
      -> task 参数修正
  -> 真正执行工具
  -> tool.execute.after
      -> 输出截断
      -> comment checker
      -> edit error recovery
      -> delegate task retry
      -> atlas verification reminder
      -> task resume info
      -> json error recovery
```

所以：

- before 阶段主要是“拦截和改参数”
- after 阶段主要是“修输出和补救”

## 4.3 事件链：系统怎么持续调度和自恢复

```text
session/message/status/error 事件
  -> plugin/event.ts
      -> dispatchToHooks()
      -> session.created / deleted bookkeeping
      -> fallback state maintenance
      -> runtime fallback / model fallback
      -> atlasHook / todoContinuationEnforcer / notifications
      -> session recovery / auto continue
```

这一层决定：

- 会话状态怎么记
- 模型失败后怎么自动切换
- 子代理完成后怎么继续
- Ralph Loop / Atlas / todo continuation 怎么“逼着系统干完”

## 五、最关键的委派链：`task(...)` 到底怎么跑

这是理解 OmO 的核心链路。

## 5.1 `task(category=...)` 链

```text
主 agent 调用 task(category="deep" ...)
  -> plugin/tool-execute-before.ts
      -> 如果有 category，强制把 subagent_type 规范成 "sisyphus-junior"
  -> tools/delegate-task/tools.ts
      -> resolveSkillContent()
      -> resolveParentContext()
      -> resolveCategoryExecution()
          -> category-resolver.ts
              -> categories 配置解析
              -> model-selection.ts 选模型
      -> executeSyncTask() 或 executeBackgroundTask()
          -> BackgroundManager 或同步子会话
```

结论：

- category 不是“直接选一个通用模型”。
- category 的真实执行体是 `Sisyphus-Junior`。
- category 真正负责的是“给 Sisyphus-Junior 选模型、给 prompt 加类别附加信息、设 fallback chain”。

## 5.2 `task(subagent_type=...)` 链

```text
主 agent 调用 task(subagent_type="oracle" ...)
  -> tools/delegate-task/tools.ts
      -> resolveSubagentExecution()
          -> subagent-resolver.ts
              -> 验证 agent 是否存在
              -> 禁止 primary agent 被 task 直接调用
              -> 解析 agent override / fallback models
      -> executeSyncTask() 或 executeBackgroundTask()
```

结论：

- 这是“点名调用具体 agent”
- 它走 agent 自己的模型/override/fallback
- 不能拿来直接调 primary-only agent

## 5.3 `call_omo_agent(...)` 链

这是另一条更直接的 agent 调用路径。

```text
agent 调用 call_omo_agent(subagent_type="explore" ...)
  -> tools/call-omo-agent/tools.ts
      -> 验证是否在允许名单
      -> 计算 fallback chain
      -> executeBackground() 或 executeSync()
```

它和 `task()` 的区别是：

- 没有 category 体系
- 没有 `load_skills[]` 这套注入机制
- 更像“直接喊一个专员去做事”

当前源码里的允许名单来自 `src/tools/call-omo-agent/constants.ts`，包括：

```text
explore
librarian
oracle
hephaestus
metis
momus
multimodal-looker
```

这比一些旧文档里写的范围更大，所以再次说明：以源码为准。

## 六、Prometheus -> Atlas -> 执行代理，这条线要单独记住

这条线是 OmO 的“计划执行闭环”。

### 第一步：Prometheus 产出计划

- Prometheus 不是普通执行代理
- 它是 planner
- 它的核心输出是 `.sisyphus/plans/*.md`

而且 `prometheus-md-only` hook 会强制它：

- 只能写 `.sisyphus/` 下的 `.md`
- 不允许直接改业务代码

### 第二步：`/start-work` 把执行权交给 Atlas

`src/hooks/start-work/start-work-hook.ts` 会：

1. 识别计划文件
2. 更新 session agent 为 `atlas`
3. 写入 `boulder` 状态
4. 告诉当前会话去读 plan 并开始执行

### 第三步：Atlas 执行计划并监督继续

Atlas 不只是一个 agent prompt，它还有 `atlasHook` 这套 continuation 机制。

也就是说：

- `Atlas agent` 负责“按计划委派”
- `atlasHook` 负责“session idle 后别停，没做完继续干”

这是一个“agent + continuation hook”双层协作设计。

## 七、每个 AI 的定位

下面只讲内置 agent。

## 7.1 顶层编排家族

| AI | mode | 核心定位 | 常见入口 | 关键限制 |
|---|---|---|---|---|
| `sisyphus` | `all` | 主编排者，负责探索、规划、委派、验证 | 默认主 agent / interactive 主会话 | 不允许 `call_omo_agent`，通过 `task` 体系做委派 |
| `hephaestus` | `all` | 自主深度执行者，偏 end-to-end 落地 | 顶层 agent 或被委派执行复杂实现 | `no-hephaestus-non-gpt` hook 限制其别跑到非 GPT 路线 |
| `prometheus` | `all` | 战略规划师，只写计划，不写业务代码 | `/plan` 家族流程 | 受 `prometheus-md-only` 强限制 |
| `atlas` | `all` | todo/plan 执行编排者，负责把计划真正做完 | `/start-work` 进入 atlas 会话 | 运行时还受 `atlasHook` 继续监督 |
| `sisyphus-junior` | `subagent` | 聚焦执行器，不负责大规模编排 | `task(category=...)` 自动落到它 | 不能用 `task(subagent_type="sisyphus-junior")` 直接点名 |

### Sisyphus

它是 OmO 的“总指挥”。

它最重要的不是写代码，而是：

- 判断当前问题该不该探索
- 判断该委派给谁
- 决定用 category 还是 direct agent
- 最后做验证和收口

它依赖 `availableAgents / availableSkills / availableCategories` 动态构建 prompt，所以它对全局能力的感知最强。

### Hephaestus

它像“高级工程师型工匠”。

定位不是 plan，而是：

- 读上下文
- 自主推进
- 尽量 end-to-end 完成实现

如果你看到“给他目标，不给他微观步骤”，基本就是在描述 Hephaestus。

### Prometheus

它是规划代理，不是执行代理。

它的职责是：

- 访谈
- 澄清需求
- 产出计划
- 必要时调用 Metis 做前置分析
- 必要时调用 Momus 做计划审查

它最大的边界是：默认不应该碰业务源码。

### Atlas

Atlas 是“执行计划的编排器”。

Prometheus 负责把活拆清楚，Atlas 负责把拆好的活做完。

Atlas 的典型工作方式：

```text
读 plan
-> 找到未完成任务
-> task(...) 派发子任务
-> 收集结果
-> 继续下一项
-> session.idle 时 atlasHook 继续驱动
```

### Sisyphus-Junior

这是 category 路由背后的真实执行代理。

它的定位非常明确：

- 聚焦
- 快速
- 少分心
- 不做大规模多层委派

你可以把它理解成“被 category 包装后的标准子执行器”。

## 7.2 专家代理家族

| AI | 定位 | 常见触发方 | 典型用途 |
|---|---|---|---|
| `oracle` | 高强度顾问/审查者 | Sisyphus, Hephaestus, ULTRAWORK | 架构评审、复杂调试、最终审查 |
| `librarian` | 外部资料和远程仓库检索员 | Sisyphus, Hephaestus, Prometheus | 官方文档、开源实现、远程仓库源代码 |
| `explore` | 本地代码库勘探员 | Sisyphus, Hephaestus, Prometheus | 找文件、找模式、找调用关系 |
| `multimodal-looker` | 图像/PDF/视觉解释器 | `look_at` tool | 看图片、看 PDF、看图表 |
| `metis` | 规划前顾问 | Prometheus | 在写计划前做意图分类和缺口分析 |
| `momus` | 计划评审员 | Prometheus | 审 plan 是否可执行、引用是否有效 |

### Oracle

Oracle 是“顾问型 agent”，不是执行工。

它适合：

- 多系统权衡
- 架构 trade-off
- 2 次以上修复失败后的复盘
- ULTRAWORK 的最终验证

它在源码里还承担一个特殊角色：

- Ralph Loop / ULTRAWORK 完成后，经常要由 Oracle 做 skeptical verification

### Librarian

Librarian 是“外部世界接口”。

它最适合：

- 查官方文档
- 查远程 repo
- 查第三方库实现
- 查变更历史、issue/PR 上下文

如果 Explore 是看“仓库内部”，Librarian 就是看“仓库外部”。

### Explore

Explore 是“仓库内部雷达”。

它最适合：

- 找定义
- 找引用
- 找文件
- 找现有实现模式

它本质是读代码，不写代码。

### Multimodal-Looker

它通常不是被主 agent 直接口头呼叫，而是被 `look_at` 工具包装调用。

真实链路是：

```text
look_at tool
  -> 创建子 session
  -> 指定 agent = multimodal-looker
  -> 传 file/image part
  -> 拉回 assistant text
```

所以它是“工具背后的视觉 agent”。

### Metis

Metis 是“计划前顾问”。

它不是 planner 本体，而是 planner 的前置咨询师。

适合：

- 意图分类
- 发现隐藏需求
- 找模糊点
- 先做 gap analysis，再让 Prometheus 正式写计划

### Momus

Momus 是“计划审稿人”。

它的关注点不是设计优不优雅，而是：

- 计划能不能执行
- 引用路径在不在
- QA 步骤能不能跑
- 是否存在真正阻塞执行的缺口

它是 blocker-finder，不是 perfectionist。

## 八、谁和谁有直接调用关系

这是给 AI 最需要记住的“关系图”。

```text
Sisyphus
  -> task(category=...) -> Sisyphus-Junior
  -> task(subagent_type=...) -> Oracle / Explore / Librarian / Metis / Momus / Hephaestus ...
  -> call_omo_agent(...) -> 快速直接调专家

Prometheus
  -> task(subagent_type="metis") 做计划前咨询
  -> task(subagent_type="momus") 做计划评审
  -> task(subagent_type="explore" / "librarian") 做调研
  -> 输出 .sisyphus/plans/*.md

start-work hook
  -> 把当前会话 agent 切到 Atlas
  -> Atlas 读取 Prometheus 计划

Atlas
  -> task(...) 派活给 Sisyphus-Junior 或其他专家
  -> atlasHook 在 session.idle 后继续追打

look_at tool
  -> Multimodal-Looker

Ralph Loop / ULTRAWORK
  -> Oracle 做最终验证
```

## 最后给 AI 的一句话总图

把这个仓库想成 4 层就够了：

```text
agents    = 决策人格层
tools     = 执行能力层
hooks     = 生命周期治理层
features  = 可复用底盘层
```

而把总调用关系想成 3 句话也够了：

```text
index.ts 负责把系统装起来
plugin/ 和 plugin-handlers/ 负责把系统接到 OpenCode 生命周期上
task()/call_omo_agent()/look_at 等工具负责把 agent 真正派出去干活
```

如果你只记一件事，就记这个：

```text
Prometheus 负责想清楚
Atlas 负责按计划推进
Sisyphus 负责主会话编排
Hephaestus 负责深度执行
Sisyphus-Junior 负责 category 落地
Oracle / Explore / Librarian / Metis / Momus / Multimodal-Looker 负责专项能力
```
